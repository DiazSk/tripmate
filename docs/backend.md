| Auto-saved drafts: `trips.status`, `promoteTripToSaved`, `purgeStaleDrafts` | Active | 2026-08-28 | Claude | A generated itinerary lived in React state until Save ran, so a Back press, a reload or a closed tab discarded a two-minute model call with nothing on disk to reopen — `generations` held the raw response, but that is an audit log keyed by run, not something the UI can render or edit. Every generation now writes a `trips` row immediately with `status = 'draft'`, and Save **promotes that same row** rather than inserting a second one: promotion is what keeps the plan's `chat_session_id`, its `generations.trip_id` link and every pre-save edit attached to the trip the traveler ends up with, where an insert-on-save would have orphaned all three. The column is nullable and backfilled once at import (`UPDATE trips SET status='saved' WHERE status IS NULL`) because every row that predates it exists *because* somebody pressed Save. `PATCH /api/trips/[id]` gained `status` (honours `"saved"` only — demotion has no caller and would silently drop a trip out of the memories wall) and `chatSessionId` (a refine replaces the conversation the plan was written in, so the row's resume handle has to move with it or a promoted trip opens its chat having forgotten the rework); the status flip runs **after** the itinerary write, so a failed write can't leave a saved trip holding the pre-edit plan. `listTrips()` now takes a status and **defaults to `"saved"`**, which is what keeps `/trip/latest` and `/profile`'s recent strip from surfacing plans nobody kept. Unkept drafts expire after `DRAFT_TTL_DAYS` (30, in `src/lib/drafts.ts`), swept on read from `/trips` and `GET /api/trips` — there is no scheduler here, and those are the only two places a stale draft would ever be seen. The cutoff is built in JS as an ISO string, not by SQLite's `datetime()`: every timestamp in this DB is `toISOString()` with a `T`, `datetime()` returns a space, and compared as strings the boundary lands in the wrong place — the same trap `tagRunsCreatedBetween` documents. Verified against the running server: a draft POST is absent from the default list and present under `?status=draft`; an autosave PATCH keeps `status='draft'` while extending `end_date`; a promote PATCH moves it between the two lists and writes the session id; a demotion attempt is a no-op; and an 88-day-old draft is swept while an 88-day-old *saved* trip and a 1-day-old draft both survive |

| `POST /api/itinerary?stream=1` streams the plan, not just the stage names | Active | 2026-09-02 | Claude | The stream carried `stage` frames and nothing else, so a client learned only which of five phases was running. It now also emits `stop` (one per completed stop, as the model writes it), `day-coords` (that day's Overpass-corrected coordinates, when the day closes — the model writes coordinates from memory and has been measured 11km out, so the camera must not use its numbers), `plan` (the itinerary is complete and interactive — **not** terminal), and `revised` (the critique's replacement day set plus its issues list). Every sink call is wrapped: a parse hiccup or a failed enqueue degrades to "no live reveal", never to a failed generation. ## Bugs

| Bug | Found | Fixed | Developer | Notes |
|---|---|---|---|---|
| `better-sqlite3`'s native binding requires Node ≥ 22; dev server started fine on Node 20 but crashed silently the moment any DB-backed route was hit | 2026-08-04 | 2026-08-04 | Aryan | Installed Node 22 via `nvm`, reinstalled `node_modules` to rebuild the native binding |
| "The planner didn't finish" — generate timing out repeatedly | 2026-08-17 | 2026-08-17 | Claude | The timeout was calibrated below the real latency. Measured across 36 successful generate calls: **p50 117s, p75 123s, p90 145s, max 165s**, against a budget of `120s + 12s/day` — so a one-day trip got 132s, *below the p90*, and the slowest tenth of runs could not finish by construction. Five consecutive failures each died exactly at their cap (156/156/156/168/192s) with the model still working. The old comment cited "~85-105s", which turns out to be roughly the 25th percentile. Base raised to 210s. The per-day term dropped 12s → 2s because duration does not track trip length: correlation between prompt size and duration across a 6× size range is **r = 0.132**, so the old term gave the most headroom to long trips and left short ones tightest — backwards. Not a regression; daily medians were flat (Aug 10: 118s → Aug 17: 117s) |
| Every LLM timeout was recorded as `error` / "exited null", never `timeout` | 2026-08-17 | 2026-08-17 | Claude | `runClaude`'s timeout handler calls `child.kill()` then writes `status: "timeout"` — but the kill fires the `exit` handler, which saw a non-zero code and overwrote the row. `llm_traces` had **zero** rows with status `timeout` despite generate timing out repeatedly, so the one failure mode worth spotting was invisible in the trace viewer and three occurrences read as unrelated glitches. Fixed with a `settled` flag guarding the exit handler; the `error` handler sets it too, so a spawn failure's ENOENT PATH hint can't be clobbered by a later "exited null" either. Reproduced and fixed-verified against the real spawn/kill/exit ordering |
| `critique` silently timing out on ~35% of runs | 2026-08-17 | 2026-08-17 | Claude | It ran on the shared `DEFAULT_TIMEOUT_MS` (90s), sized for small lookups, while actually being a full-itinerary reasoning pass — 7 of 20 calls died at exactly 90s (successful ones run p50 58s / p90 75s, so the real tail extends past the ceiling). The runner catches critique failures by design *and reported `critique: done` regardless*, so a third of trips shipped with no budget/timing review and the loader said the review had happened. Now has its own `CRITIQUE_TIMEOUT_MS` (150s) and reports `skipped` when it didn't run — a status already in the stage vocabulary that the progress strip renders distinctly, so honesty here needed no new UI |
